HydroGo documentation.

Understand the engine, build a Client Edition, and operate it with clear boundaries.

HydroGo is a Go Workspace and product engine. HydroCore supplies shared, versioned contracts; optional modules provide capabilities; a Client Edition chooses what runs and owns its business rules. This guide is written for developers and operators.

Read capability claims with their status. This page explains contracts and available workflows; it does not certify every combination for production. The scope and status section explains what requires Edition wiring or environment-specific validation.

Quick start

Start with the CLI help, scaffold an Edition, then validate its configuration before starting runtime services. The example uses the News preset; the enabled modules in your manifest determine what the process actually composes.

Create and inspect

hydro help
hydro project new news-room --preset=news
cd news-room
hydro project check --config config.yaml
hydro validate --config config.yaml

project check checks the project and generated resources without opening a database. validate checks runtime configuration and module constraints. For local development use hydro run; hydro dev is the compatible alias. The development proxy listens on 127.0.0.1:8090 by default.

Develop and verify

hydro run
hydro test --package ./modules/news/... --timeout 2m

A generated Edition may need a prepared data directory and a valid hydro.lic license file; official release binaries refuse to start without one. A source-built, non-official binary can opt into hydro serve --dev with the --dev flag or HYDRO_DEV_MODE=1, which skips license validation but is forced to bind only to 127.0.0.1/localhost and prints an impossible-to-miss "UNLICENSED DEV MODE" warning to stderr. For deployment, review and apply migrations explicitly before serving traffic.

Architecture

The system is a modular monolith with explicit composition. The shared engine is never forked for one customer. General capabilities become versioned Core or Module contracts; customer policy and integration behavior live in the Client Edition.

BlueprintSchema, module selection, and version lock
GeneratedTyped models, repositories, and transport scaffolds
CustomAuthorization, workflows, and integrations
RuntimeExplicit route, adapter, and worker composition
HydroCore
Common application contracts, security infrastructure, CLI, and release machinery.
Hydro Modules
Optional capabilities such as Pages, News, Site, Media, and Forms.
Client Edition
The selected modules, manifest, theme, generated artifacts, and human-owned policy.
Adapters
Database, cache, media, and provider implementations behind domain contracts.

The dependency direction is HTTP/HTML or JSON transport → application service → module-owned repository interface → certified storage adapter. Domain and application code must not depend on SQL dialect or cache-driver details. An inactive module must add no routes, migrations, assets, workers, or mandatory infrastructure.

Request flow

A request enters a classified route and bounded middleware chain. Authentication, authorization, tenant resolution, and CSRF checks are applied where required. The application service validates input and owns transitions; the repository adapter persists data. The response is rendered as server HTML or versioned JSON for the intended audience.

01 · RoutePublic or protected access, request limits
02 · PolicyIdentity, role, tenant, and mutation checks
03 · ServiceValidation, transaction, repository, audit
04 · ResponseAccessible HTML or bounded JSON

Durable side effects can be recorded in an outbox and delivered by bounded workers. Audit records describe consequential actions. A failure shown to a public visitor or member stays actionable and free of internal SQL, stack traces, tokens, or infrastructure detail.

Workspace & Client Editions

Blueprints automate proven repetition. Machine-owned output stays under generated/; edit the blueprint or generator to change it. Human-owned policy, workflows, authorization, and integration code stay under custom/.

  1. Choose the Edition manifest, capacity profile, enabled modules, and version lock.
  2. Validate the blueprint; generate typed models, repository interfaces, route metadata, SDK contracts, and migration proposals.
  3. Review permissions, tenant scope, migrations, cache behavior, and external effects in the Edition composition root.
  4. Run contract tests and explicitly enable the route or resource.

The generator does not execute DDL, invent authorization, or silently activate a module. A generated route helper is a composition primitive, not an automatically exposed endpoint. Production UI should use typed server-rendered components; HTMX is limited to registered attributes and explicit mutation contracts.

Modules & capabilities

An Edition enables only the capabilities it needs. The module registry and Edition manifest determine routes, migrations, assets, workers, and storage responsibilities.

Commerce is deferred as a general Core capability. An Edition must not infer a production-ready payment flow from older plans or examples. Optional AI, GraphQL, Redis, object storage, and other providers likewise depend on explicit build and deployment choices.

Data, cache & migrations

SQLite is the compact local default. PostgreSQL and MySQL/MariaDB adapters are evaluated against the same behavioral contract and carry certified schema and migration tests. Migration files are dialect-aware, immutable after application, and accompanied by compatibility and recovery metadata.

  • Migration: validate all three dialects, review metadata, and apply as an operator action. Serving traffic must not silently perform DDL.
  • Multi-tenancy: most records belong to a tenant; tenant identity is resolved in request middleware and enforced at the record level before reads, writes, cache access, jobs, and media operations. The tenant registry and bootstrap are their own migration; one tenant's data cannot leak into another tenant's query or cache key space.
  • Transaction: application services define boundaries; outbox records keep durable effects tied to committed state.
  • Cache: define the tenant-aware key, TTL, invalidation path, stampede protection, and safe failure fallback.
  • Portability: export/import uses an allowlist and excludes secrets, session state, and unrelated runtime data.
  • Recovery: backups include integrity evidence; restore is staged, checked, and activated by an operator.

Compact installations must not pay for idle services. Larger capacity profiles bound connection pools, worker concurrency, and admission/backpressure according to measured load rather than a universal hardware promise.

APIs & integration

HydroGo exposes versioned JSON contracts alongside server-rendered HTML. Public content, staff mobile, and member mobile APIs are separate audiences with separate authentication and authorization boundaries.

SurfaceUseContract rule
Public content APIPublished content for external frontends.Bounded queries, stable fields, locale and visibility policy.
Staff mobile APIAuthorized editorial and operational client actions.Staff token lifecycle, role and tenant checks.
Member mobile APIMember profile and private resources.Distinct member identity and ownership checks.
Generated resource APIEdition-defined collection or singleton resources.Version lock, allowlisted fields, explicit route composition.
Webhooks & SDKExternal delivery and typed clients.Retries, idempotency, compatibility, and bounded payloads.

OpenAPI files in the repository are the wire-contract source of truth. Within the running product, clients should rely on the Edition’s published contract and not assume every optional endpoint exists. Mutations require authorization, tenant scope, CSRF for browser flows, and defined idempotency behavior.

Security & data lifecycle

Default deny is the starting point. Routes declare access class; services enforce record-level authorization; output is escaped, rich content sanitized, sessions protected, and sensitive actions audited.

  • Admin, sysadmin, developer, auditor, and public/member interfaces show different levels of detail.
  • Tenant identity is resolved before tenant-scoped reads, writes, cache access, jobs, and media operations.
  • Browser mutations declare target, swap, CSRF, authorization, tenant scope, and idempotency.
  • Secrets and internal diagnostics belong in controlled operator systems, not end-user responses.
  • Retention, erasure, portable export, and backup recovery have explicit data-lifecycle policies.

Security tests and local validation do not replace provider, device, penetration, and real deployment exercises. Release evidence must state its environment and limits.

Admin Studio & UI

Admin Studio serves editors and business operators. It should foreground content and workflow decisions; infrastructure metrics and raw technical errors belong to the operator surface. Generated server-rendered views use typed Design System components for escaping, accessibility defaults, and visual tokens.

HTMX is an allowlisted enhancement layer, not a client-side state replacement. Tailwind is compiled at build time for approved isolated surfaces and themes; the production binary carries static CSS, not a Node or browser runtime dependency. The documentation itself uses a dedicated compiled Tailwind stylesheet and does not load an Admin Studio theme.

Deployment & operations

The executable embeds release-owned assets. Configuration, database, media, secrets, logs, and backups remain in external persistent storage. A deployment chooses a capacity profile and only the optional services required by its Edition.

A deliberate release sequence

hydro validate --config config.yaml
hydro migrate --config config.yaml
hydro doctor --config config.yaml
hydro serve --config config.yaml

Before release, check health and readiness, migration compatibility, session/media/asset continuity, background jobs, backup integrity, and rollback steps. Blue/Green changes follow an expand–migrate–contract sequence so old and new binaries can coexist during the transition.

Backup and restore are operator-controlled. A restore is verified in staging before activation; destructive cleanup and retention are bounded. Observability provides logs, metrics, traces, and alarms appropriate to the deployment profile without exposing internal diagnostics to members.

Safe Mode: a reversible incident-recovery control enabled by YAML safe_mode, the HYDRO_SAFE_MODE environment variable, or the --safe-mode flag. It stops the mail, news publication, webhook outbox, and monthly link-audit workers (and CGI lazy cron does not dispatch that work either); durable queued records remain stored for later delivery. Password login, MFA, local session cleanup, IP blocklist refresh, and content editing stay active. Admin Studio shows a high-visibility warning while it is enabled; during a Blue/Green cutover, make sure both instances run in the same mode intentionally.

Hosting profiles

The same compiled binary fits three hosting models under the same route/authorization/worker contract: a long-running server process, a shared host's FastCGI manager, and process-per-request CGI. The choice depends on traffic, background-job needs, and the access a provider actually grants.

ProfileBackground workRecommended databaseRequirement
VPS / container
hydro serve		All resident workers run (media derivatives, session cleanup, news polling, webhooks) with a bounded connection pool.SQLite (Compact) or PostgreSQL.SSH access, a process manager (systemd/Docker), and a TLS-terminating reverse proxy (Nginx/Caddy).
Shared hosting — FastCGI
hydro serve --fastcgi		The same resident worker set, running as a long-lived process bound to loopback.PostgreSQL or MySQL recommended; SQLite also works.The provider's FastCGI process manager (e.g. Passenger) and Apache/Nginx proxy integration.
Shared hosting — CGI
hydro.cgi + .htaccess		No resident workers; each request runs a bounded lazy cron that leases at most four jobs within a five-second budget.MySQL/MariaDB recommended (removes the multi-process file-locking risk); SQLite also works at low traffic.Apache + .htaccess only; no SSH required.

VPS or container

The long-running model keeps every worker and the connection pool, giving the widest feature coverage.

Release sequence

hydro validate --config config.yaml
hydro migrate --config config.yaml
hydro doctor --config config.yaml
hydro serve --config config.yaml

Run the binary under a process manager such as systemd, behind a TLS-terminating reverse proxy (Nginx/Caddy); hydro serve should not be exposed directly. During a Blue/Green cutover, the old and new binaries can coexist following an expand–migrate–contract sequence.

Shared hosting: FastCGI

FastCGI keeps resident workers alive because it runs a persistent request loop; net/http/cgi does not.

hydro serve --fastcgi --fastcgi-address 127.0.0.1:9001

This address is bound to loopback by default; point the provider's Apache FastCGI integration at it. Process supervision and proxy configuration belong to the hosting provider.

Shared hosting: CGI

CGI starts a fresh process per request, so resident workers are disabled; scheduled work such as News instead advances through a bounded "lazy cron" that leases at most four jobs per request.

Setup

make build
# Copy the binary to the document root as "hydro.cgi" and make it executable
# Place deploy/hosting/.htaccess alongside it

Anonymous, query-free, cookie-free public page and news HTML responses are written under DOCUMENT_ROOT/static_cache; on a cache hit Apache serves the file directly and the CGI process never starts. Page/News mutations invalidate the cache; clear this directory by hand after any out-of-band database change. Using MySQL/MariaDB instead of SQLite is recommended to avoid concurrent CGI processes contending for the same file lock.

Contributing & verification

Before changing behavior, read the product philosophy, information hierarchy, implementation plan, architecture index, and affected ADRs. A change to a module boundary, contract, route, or migration needs a full ADR and its implementation evidence. A behavior-preserving fix inside one module needs a concise change note.

Focused and repository checks

hydro test --package ./modules/news/... --timeout 2m
go test ./...
go run ./tools/moduleguard -root modules -allow modules/api
go run ./tools/migrationguard -root migrations

Importguard, moduleguard, and migrationguard remain mandatory CI gates. New or modified modules must account for database parity, migration recovery, cache invalidation, Compact footprint, concurrency budgets, Blue/Green compatibility, session and media continuity, security, auditability, and data lifecycle.

Scope, status & terminology

HydroGo is a Workspace that produces Client Editions. Code and local contract tests prove a bounded behavior; they do not by themselves prove that every provider, deployment profile, or customer environment is production-certified.

Implemented
Code and relevant local tests exist for the stated scope.
Planned
A design or task exists; delivery evidence is still missing.
Open gate
A real environment, provider, operational, or legal validation remains.
Not supported
Intentionally outside the present contract; an alternative should be stated.

Examples of open production gates

Real two-process Blue/Green rollback behind a reverse proxy, customer-like backup and restore with measured RPO/RTO, provider-side object-storage IAM/KMS and failover, multi-node Redis failure exercises, external extension browser tests, mobile device-loss and abuse drills, and commercial licensing/legal review require evidence from their actual environments. Local contract tests do not close these gates.

Architecture decisions explain why a boundary exists. Validation reports record actual commands, environment, results, and limitations. The implementation plan defines scope and acceptance criteria. Always read these together when making a release claim.
