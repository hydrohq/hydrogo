# ADR-0270: Opt-in direct MX mail fallback

- **Status:** Accepted
- **Date:** 2026-09-28
- **Related:** [ADR-0267](0267-form-leads-and-mail-spool.md), [ADR-0011](0011-consistency-upgrade-and-recovery.md), [ADR-0024](0024-optional-redis-rate-limiting-and-queue-boundary.md)

## Context

Some small deployments have no SMTP submission provider. Direct delivery to a
recipient's MX can help staging and low-volume deployments, but it depends on
outbound TCP port 25, receiver policy, DNS, sender reputation, and valid sender
domain configuration. It is not a reliable replacement for a configured mail
provider.

## Decision

When no SMTP host is configured, a non-empty `mail.from` explicitly enables
direct MX delivery. The sender resolves the recipient domain's MX records,
tries them in priority order, uses SMTP STARTTLS with normal certificate
verification, and does not authenticate to the receiving MX. Delivery failures
are retried by the existing durable spool. Forms inactive still creates no
spool worker or form resources; account mail uses the same selected sender.

The direct path never invents a sender identity or bypasses TLS. It requires an
operator-supplied sender address. DKIM signing is deferred until a separate
signing-key and rotation contract exists; SPF is a DNS policy, not a message
header, and cannot be generated by the sender. Direct MX delivery is therefore
not advertised as authenticated or guaranteed to reach the inbox. A configured
SMTP submission host always takes precedence.

## Compatibility and operations

The setting is backward-compatible: existing SMTP configurations are
unchanged, and empty mail settings disable delivery. Operators should use a
submission provider for production and may disable direct delivery by removing
`mail.from`. The spool remains the durable local maildrop when port 25 is
blocked or MX delivery is refused. No migration is required.

## Consequences

- Staging can attempt delivery without provider credentials while retaining
  failed messages locally.
- Receiver policy, reputation, and port-25 filtering can prevent delivery;
  retries do not remove those external limits.
- Message delivery remains at-least-once after ambiguous SMTP responses.
