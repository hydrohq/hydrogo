# ADR-0337: `hydro dev` entrypoint for scaffolded Client Edition projects

- **Status:** Accepted
- **Date:** 2026-10-01
- **Related decisions:** [ADR-0058](0058-hydro-dev-entrypoint.md), [ADR-0028](0028-core-isolation-and-licensing.md)

## Context

`hydro dev` (ADR-0058) always shells out to `go run ./tools/devserver` in the
current working directory. That is correct for a HydroGo Core checkout, but
a project scaffolded by `hydro new`/`hydro generate scaffold` (a "Client
Edition" project, per ADR-0028) has no `go.mod` and no `tools/devserver` —
it ships only `config.yaml`, `themes/`, `migrations/`, `custom/`, `seed/`
and `hydrogo.lock`. Running `hydro dev` from such a project fails with
`go: go.mod file not found in current directory or any parent directory`.
This was found and documented during an end-to-end scaffold verification
task (`projeler/hydrogo/TASKS.md`, "verify `hydro new` + `hydro generate scaffold`
chain end-to-end").

Verified behavior of the already-compiled `hydro` binary against a freshly
scaffolded Client Edition project (preset `editorial`), without any vendor
license:

- `hydro migrate --config config.yaml` succeeds without a license. It does
  need the SQLite database's parent directory to exist first — a fresh
  `hydro new` scaffold has no `data/` directory yet.
- `hydro seed-demo --confirm-demo --config config.yaml` succeeds without a
  license.
- `hydro serve --config config.yaml` fails with "license file not found
  (hydro.lic)" because every project generated by `internal/projectgen`
  hard-codes `license.required: true` in `config.yaml`
  (`cmd/hydro/license_cmd.go`'s `validateRuntimeLicense` only skips
  enforcement when `license.required` is `false`). A locally self-signed
  `hydro.lic` (via `hydro-issuer keygen`/`issue`) is also rejected, because
  runtime verification requires the vendor public key baked into the
  official build — this is documented, intentional behavior (ADR-0028,
  "Key Trust"), not a bug.

So a Client Edition `hydro dev` can legitimately run its migrate/seed/watch
loop, but the `serve` child process it supervises will not become healthy
until a real `hydro.lic` is present — the same constraint `hydro serve`
already has on its own. Producing a vendor-independent dev/trial license is
tracked separately (`projeler/hydrogo/TASKS.md`, "Scaffolded Client
Edition projects unable to perform unlicensed local e2e verification") and is out of
scope here.

## Decision

1. **Mode detection, not a flag.** `hydro dev` (`cmd/hydro/main.go`,
   `devCommand`) inspects its working directory and picks an implementation:
   - `isCoreCheckout(root)`: `go.mod` **and** `tools/devserver/` both exist
     → unchanged `coreDevCommand` (byte-identical body to the previous
     `devCommand`, i.e. `go run ./tools/devserver <args>`).
   - `isClientEdition(root)`: `hydrogo.lock` **and** `config.yaml` both
     exist → `runEditionDev` (`cmd/hydro/dev_edition_cmd.go`).
   - Neither → a explicit error naming both expected layouts.
   - The HydroGo Core repository itself also carries a root-level
     `config.yaml`/`hydrogo.lock` (for its own local dev/testing), so the
     two signals are not mutually exclusive in practice; the Core checkout
     is checked first and wins, so no existing Core-repo workflow changes.
2. **No `go build` in Client Edition dev mode.** A Client Edition project
   has no Go source at all, so there is nothing to compile. `runEditionDev`
   resolves the already-running `hydro` binary via `os.Executable()`
   (overridable through `HYDRO_DEV_SELF_BINARY`, used by tests) and
   subprocesses `migrate`, optionally `seed-demo`, and `serve --config
   ... --address ...` against it. The binary itself never changes while
   `hydro dev` runs, so — unlike `tools/devserver` — there is no "previous
   binary" fallback; a failed restart just leaves the error visible in the
   status overlay instead of silently reverting.
3. **File watch is scoped to what a Client Edition project can actually
   contain:** `config.yaml`, `hydrogo.lock`, and everything under
   `themes/`, `migrations/`, `custom/`, `seed/`. `.go` files are
   deliberately not part of the watch set (there are none). `.css`/`.js`
   files under a theme's `static/` directory are asset-only updates (no
   migrate/restart), matching `tools/devserver`'s existing asset rule.
4. **The reverse proxy, "building/ready" browser overlay, and status
   endpoint are a bounded copy, not a shared package.** `tools/devserver`
   is intentionally left untouched (it owns the Core rebuild-from-source
   flow); `dev_edition_cmd.go` defines its own `statusPath`/`clientPath`/
   `stylePath`, state machine, and HTML/JS/CSS strings. Extracting a shared
   package was considered and rejected as premature — the two dev modes
   have different restart semantics (rebuild vs. no-build) and the
   duplication is small and unlikely to need to change in lockstep.
5. **License failures surface honestly.** When the `serve` child process
   cannot become healthy (most commonly because `config.yaml` has
   `license.required: true` and no `hydro.lic` is present), the dev proxy
   reports a "Not Ready"/error status instead of a false "Ready" — the same
   contract `tools/devserver` has for build failures.

## Alternatives

- **Vendor `tools/devserver` as a standalone module the Client Edition
  could depend on:** rejected — would require shipping Go source/tooling
  into Client Edition projects, contradicting ADR-0028's Core isolation.
- **Have `hydro new` scaffold a `.tmp`-style copy of `tools/devserver`
  into the project:** rejected — duplicates a moving target across every
  generated project instead of once in Core, and still implies `go.mod`.
- **Make `hydro dev` always rebuild via `go build ./cmd/hydro` even in
  Client Edition mode:** not possible — there is no `cmd/hydro` source in
  a Client Edition project.

## Consequences

### Benefits

- `hydro dev` works in scaffolded Client Edition projects instead of
  failing with a Go toolchain error.
- Core's `hydro dev` behavior is provably unchanged (`tools/devserver`
  untouched, `coreDevCommand` is the prior `devCommand` body verbatim,
  `go test ./tools/devserver/...` passes unmodified).
- The pre-existing "Client Edition dev mode without a license" limitation
  is now surfaced through the same honest status overlay used for build
  failures, instead of an opaque `go.mod` error.

### Costs and risks

- Duplicated (not shared) proxy/overlay code between `tools/devserver` and
  `dev_edition_cmd.go`; a deliberate, bounded trade-off (see Decision #4).
- `hydro dev` in Client Edition mode is still not useful for reaching a
  "Ready" `/healthz` without a valid `hydro.lic`; that gap is tracked
  separately and not solved by this change.

## Scale impact

- Compact: unaffected; this is a local developer-tooling change only.
- Standard / Distributed: not applicable — `hydro dev` is local-only in
  both Core and Client Edition modes.

## Database impact

- SQLite: `runEditionDev` creates the configured SQLite DSN's parent
  directory before the first `migrate` call, since a fresh `hydro new`
  scaffold has no `data/` directory yet.
- PostgreSQL: unaffected (no directory bootstrap needed).
- Future adapters: unaffected.

## Cache impact

None; no caching behavior is introduced.

## Deployment and compatibility

`hydro dev` is a local-only developer command; it has no production
deployment impact. The binary continues to support both a Core checkout and
a Client Edition project from the same `hydro dev` invocation without a
flag, determined purely by the working directory's contents.

## Validation

- `go test ./cmd/hydro/...` — unit tests for `isCoreCheckout`/
  `isClientEdition`/`detectDevMode`, plus an integration test that builds a
  real `hydro` binary, scaffolds a Client Edition project (with
  `license.required: false` to isolate the dev-mode orchestration from the
  separately tracked licensing gap), runs `hydro dev`, polls `/healthz`
  until 200, edits a theme static asset (expects an asset-only update, no
  restart) and a theme layout file (expects migrate+restart, then healthy
  again).
- `go test ./tools/devserver/...` passes unmodified — zero regression on
  the Core dev path.
- `go test ./internal/projectgen/...` passes after the generated project
  README template gained a documented `hydro dev --config config.yaml`
  step with the verified license caveat.
- `go vet ./...`, `gofmt -l .` (empty), `scripts/adr-drift-check.ps1`.
